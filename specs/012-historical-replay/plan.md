# Implementation Plan: Historical Replay

**Branch**: `012-historical-replay` | **Date**: 2026-07-29 | **Spec**: [spec.md](./spec.md)

## Summary
Add a thin `ReplayService` wrapper around the existing `CreateOptimizationRunHandler` (009) plus
the as-of filtering it already performs (`InventoryLot.AsOfDate`, `Order.RequestDate`). A replay is
just an `OptimizationRun` for a historical as-of date, with an independent leakage audit and the
model/optimizer/costing versions used recorded alongside it. A separate regret report compares that
optimizer run to two simple, deterministic baseline policies over a date window, using the same
`AllocationInput` shape (facilities/products/lots/orders/trucks) so the comparison is apples-to-apples.

## Approach
1. **Domain**: add `ReplayRun` (links a generation + as-of date to the `OptimizationRun` it produced,
   plus the model/optimizer/costing versions and leakage audit used) and `ReplayWindowReport` (a
   persisted regret report for a date window, `ReportJson` holding the day-by-day comparison).
2. **Persistence**: extend `DairyDnaDbContext`/`IDairyDnaDbContext` with `ReplayRuns` (indexed by
   generation+as-of, unique per `OptimizationRunId`) and `ReplayWindowReports`.
3. **Application — `ReplayService`**:
   - `RunAsync`: validates the as-of date falls inside the generation's `StartDate`–`EndDate`, runs
     an independent leakage audit (confirms every `InventoryLot`/`Order` row that could be pulled for
     that as-of has an effective date on or before it; for non-Spot price modes also checks the price
     forecast rows used), calls `CreateOptimizationRunHandler.HandleAsync` with the requested
     `PriceMode`, stamps the generation's preferred (published, else newest non-retired) supply/
     demand/price model version ids, the optimizer version actually used, and
     `TransportCostCalculator.CostingModelVersion`, then persists a `ReplayRun` linked 1:1 to the new
     `OptimizationRun`.
   - `GetAsync` / `ListAsync`: read replay runs (optionally filtered by as-of date) joined with their
     linked `OptimizationRun` status/objective/unserved/unused counts.
   - `BuildRegretReportAsync`: for each day in the window, reuses (or runs) a Spot replay, then builds
     the same `AllocationInput` the optimizer used and runs two simple baseline policies against it —
     `NearestCustomerGreedy` (fill each lot from the geographically nearest open order for the same
     product) and `HighestPriceFirst` (fill highest-offered-price orders first from available
     inventory). Baselines ignore truck time-window/capacity feasibility — documented proxy
     economics, not an alternate feasible optimizer. A day "wins" for the optimizer when its objective
     exceeds the best baseline's by more than the 0.01 reproducibility tolerance; the window summary
     states explicitly whether the optimizer met the bar on at least one day. The report is persisted
     as `ReplayWindowReport`, and a sample is checked in at
     `specs/012-historical-replay/fixtures/regret-window-sample.json` (generated by a unit test).
4. **API**: `/api/replay/runs` (POST/GET/GET by id) and `/api/replay/reports/regret` (POST) +
   `/api/replay/reports/{id}` (GET).
5. **UI**: `/replay` — pick/paste a generation, a day scrubber (range input) across the dataset's
   `StartDate`–`EndDate`, run/view a replay for the selected day (reusing the demo network map +
   optimization-run recommendation highlights), and a regret-report section with a grouped-bar SVG
   comparing total optimizer vs. baseline contribution margin over a chosen window.

## Non-goals
- Re-training forecast models per replay day (Spot mode is the default; `ForecastPoint` reuses the
  existing 009 forecast-price overlay and is not otherwise changed).
- A third baseline policy, or feasibility-accurate (truck capacity/time-window) baseline routing.
